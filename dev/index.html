CTModels.jl ​

CTModels.jl is the model layer of the control-toolbox ecosystem. It defines how an optimal control problem (OCP), its numerical solution and an initial guess are represented, and nothing else: it neither parses, discretises nor solves.

Who this documentation is for

This site documents CTModels for developers of the control-toolbox packages and for experienced users who work with the model objects directly. To model and solve optimal control problems, start with OptimalControl.jl, which wraps CTModels behind the @def DSL and solve.

Place in the ecosystem ​

text
   CTParser ── @def ──► PreModel ── build ──► Model ◄──────────────────┐
                        (CTModels.Building)   (CTModels.Models)        │
                                                │                      │
                         CTDirect (direct) ─────┤                      │
                         CTFlows (indirect) ────┤                      │
                                                ▼                      │
                    solver output ── build_solution ──► Solution ──────┘
                                    (CTModels.Solutions)  │
                                                          ├─► Init (warm start)
                                                          ├─► Serialization (JSON, JLD2)
                                                          └─► PlotCase ─► Plots / Makie

  • CTParser.jl turns the @def DSL into calls to the Building verbs (state!, dynamics!, constraint!, …) and build.

  • CTDirect.jl discretises a Model into an NLP and turns the NLP solution back into a Solution with build_solution.

  • CTFlows.jl builds Hamiltonian flows from a Model and returns Solution objects as well.

  • CTSolvers.jl provides the resolution infrastructure (NLP solvers, modelers, ODE integrators) used by CTDirect and CTFlows.

  • OptimalControl.jl re-exports a selection of CTModels symbols for end users.

Conventions ​

Qualified access

CTModels exports no symbol at the package level. Each submodule exports its public API and the package brings the submodules in, so every public symbol is reached as CTModels.symbol, for example CTModels.state! or CTModels.build_solution; this is the form used throughout this documentation. The fully qualified form CTModels.Building.state! refers to the same function.

  • One-dimensional is scalar. A one-dimensional state, control or variable is a Number, never a length-1 vector: user functions receive u, not u[1], and solution and initial-guess trajectories return scalars.

  • In-place functions. Dynamics and nonlinear constraints are written in place, f!(r, t, x, u, v) and b!(r, x0, xf, v), with the full argument list even for an autonomous problem.

  • Structured errors. Invalid inputs raise the typed exceptions of CTBase.Exceptions (IncorrectArgument, PreconditionError, ExtensionError, …), with a message, the received and expected values, and a hint.

How this documentation is organised ​

  • Getting started: a model, a solution and an initial guess in five minutes.

  • OCP model: the PreModel → build → Model pipeline, the type and trait architecture, each declaration verb, and the display of models.

  • Solutions: the anatomy of a Solution, the build_solution contract for solver authors, time grids, trajectories, duals and diagnostics.

  • Initial guesses: input formats, validation and warm start.

  • Extensions: export and import, plotting with Plots and Makie, and the plotting architecture.

  • Performance: the hot path / setup path rule and how type stability is checked.

  • API Reference: one page of public symbols per submodule, and one page of internals (private symbols and extensions).
